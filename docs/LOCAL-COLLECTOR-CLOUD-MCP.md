# 로컬 수집 앱 + Cloudflare 저장·조회 + ChatGPT MCP 설계

작성일: 2026-10-05

## 방향

현재 e-Class MCP의 학교 로그인·자료 수집 기능을 사용자 노트북에서 주기적으로 실행하는 앱으로 분리한다.
앱이 수집한 공지·강의·과제·자료 목록과 문서 파일을 Cloudflare 쪽에 동기화하고,
ChatGPT용 원격 MCP는 이 동기화본을 검색·조회·제공한다.

학교 비밀번호·쿠키·Canvas/LearningX 토큰은 로컬 앱에 보관한다.
클라우드에는 사용자가 동기화하는 학습 데이터와 우리 서비스의 연결 정보가 저장된다.
노트북이 꺼져 있어도 ChatGPT는 마지막으로 동기화된 데이터를 사용할 수 있다.

## 이 방향을 선택한 이유

- 사용자마다 로컬 수집을 실행하고 학교 인증 정보를 기기에 보관한다.
- 사용자는 Cloudflare 계정이나 개인 서버를 준비하지 않고 앱을 설치해 연결한다.
- 학교 인증 정보를 우리 서버에 보내지 않고 사용자의 자격증명 저장소에 유지한다.
- 조회는 클라우드 동기화본으로 처리하므로 노트북의 외부 접속 주소나 인바운드 터널이 필요하지 않다.
- 공지·자료·과제를 별도 DB에 저장하면 과목을 넘나드는 검색, 최신 공지, 주간 자료, 마감일 목록을 구성할 수 있다.

로그인·SSO와 자료 수집은 HTTP로 처리한다.
세션 구성과 검증 방법은 [HTTP 세션](HTTP-SESSION.md)에 있다.
자료 구성과 검증 방법은 [HTTP 자료 수집](HTTP-MATERIALS.md)에 있다.

## 전체 구조

```text
학교 e-Class
    ↑ HTTP 요청 / 로컬 학교 세션
사용자 노트북의 수집 앱
    │ 기기 인증 + 변경분 업로드
    ↓
Cloudflare API / Worker
    ├─ 사용자·기기·연결 인증
    ├─ 동기화 수신 및 작업 큐
    ├─ 메타데이터 DB: 강의·공지·과제·자료 목록·동기화 상태
    └─ R2: 문서 파일
    ↑
원격 MCP: 검색·조회·파일 제공
    ↑ 사용자 OAuth 연결
ChatGPT
```

로컬 앱은 서버로 나가는 HTTPS 통신을 사용한다.
원격 MCP의 일반 조회는 항상 DB와 R2를 사용한다.
즉시 갱신이 필요할 때는 서버에 동기화 작업을 등록하고 로컬 앱이 가져가서 실행한다.

## 구성 요소의 역할

| 구성 요소 | 역할 |
| --- | --- |
| 로컬 수집 앱 | 학교 로그인, 세션 갱신, 주기적 수집, 변경 감지, 문서 다운로드, 업로드, 작업 수신 |
| CF API | 기기 인증, 사용자 소유권 판별, 메타데이터 수신, 파일 업로드 권한 발급, 작업 상태 관리 |
| 메타데이터 DB | 정규화된 학습 데이터와 원본 ID, 사용자별 접근 관계, 마지막 동기화 시각 저장 |
| R2 | 사용자별 문서 파일 저장 |
| 원격 MCP | 사용자 인증 후 검색·조회·문서 제공, 동기화 요청 등록 |

기존 MCP 코드는 수집 엔진으로 재사용한다.
학교에 접속하는 로직과 ChatGPT에 도구를 제공하는 로직을 분리하는 것이 핵심이다.

## 사용자 연결과 자격증명

사용자 계정, 로컬 기기, ChatGPT 연결을 서로 구분한다.

| 자격증명 | 보관 위치 | 용도 |
| --- | --- | --- |
| 학교 ID·비밀번호 | 로컬 OS 키체인 또는 암호화 저장소 | 학교 로그인과 세션 갱신 |
| 학교 쿠키·API 토큰 | 로컬 자격증명 저장소 | 학교 자료 수집 |
| 우리 서비스의 기기 토큰 | 로컬 자격증명 저장소 | 동기화 업로드와 작업 수신 |
| ChatGPT용 OAuth 토큰 | ChatGPT 연결 계층 | 해당 사용자의 클라우드 데이터 조회 |

초기 연결 흐름:

1. 사용자가 앱을 설치하고 우리 서비스 계정으로 로그인한다.
2. 앱을 해당 계정의 기기로 등록하고 기기별 토큰을 발급한다.
3. 사용자가 앱에서 학교 계정을 설정한다. 앱이 로컬에서 로그인하고 저장한다.
4. 동기화할 강의와 문서 업로드 범위를 선택한다.
5. 앱이 첫 동기화를 수행한다.
6. 사용자가 ChatGPT에서 우리 원격 MCP를 OAuth로 연결한다.

별도의 앱용 ID·비밀번호를 추가하기보다 계정에 기기를 연결하고 기기 토큰을 발급한다.
서버는 기기 토큰을 해시로 저장하고, 요청을 인증한 뒤 사용자 ID를 결정한다.
업로드 바디에 들어 있는 사용자 ID를 소유권 판단에 사용하지 않는다.

기기 토큰은 해당 사용자의 업로드·작업 수신 권한을 가진다.
ChatGPT 연결은 해당 사용자의 조회·동기화 요청 권한을 가진다.
기기 연결과 ChatGPT 연결은 각각 회수할 수 있다.

## 주기적 수집

초기 주기 제안:

| 대상 | 주기 | 처리 |
| --- | --- | --- |
| 공지·과제·마감일 | 30분 | 목록 확인 후 추가·변경 항목 반영 |
| 강의자료 목록 | 1시간 | 추가·변경 자료 반영 |
| 수강 강의 목록 | 하루 | 강의 목록과 접근 상태 갱신 |
| 문서 파일 | 새 자료 발견 또는 사용자 요청 | 다운로드 후 업로드 |

앱 시작·절전 복귀·네트워크 복구 때 마지막 동기화 시각을 확인하고 밀린 대상을 갱신한다.
누락된 주기마다 작업을 재생하지 않고 현재 상태를 한 번 수집한다.
동시에 같은 동기화가 중복 실행되지 않게 로컬 실행 잠금을 둔다.

매번 전체 데이터를 다시 업로드하지 않는다.
학교의 원본 ID, 수정 시각, 내용 해시를 이용해 변경분을 판단한다.
파일은 내용 해시를 비교해 같은 버전의 중복 업로드를 줄인다.
실패 시 재시도 간격을 늘리고 사용자·강의별 요청 시점을 분산한다.

목록에서 사라진 항목의 삭제 처리는 해당 목록 전체 수집이 성공한 뒤 수행한다.
일부 페이지 조회 실패나 일시적인 인증 오류를 자료 삭제로 처리하지 않는다.

## 저장할 데이터

메타데이터 DB 후보는 D1이며, 파일은 R2에 저장한다.

| 데이터 | 주요 필드 |
| --- | --- |
| 강의 | 원본 강의 ID, 이름, 학기, 교수, 사용자 접근 관계 |
| 공지 | 원본 공지 ID, 강의 ID, 제목, 본문, 게시·수정 시각, 첨부 연결 |
| 과제 | 원본 과제 ID, 강의 ID, 제목, 안내, 마감일, 조회된 개인 상태 |
| 자료 | 원본 자료 ID, 출처, 강의 ID, 제목, 종류, 공개·잠금 상태, 파일 연결 |
| 파일 | 사용자 소유권, 자료 연결, R2 객체 키, 내용 해시, 크기, MIME, 버전 |
| 동기화 상태 | 사용자·기기·강의·수집 대상, 시도 시각, 성공 시각, 오류 상태 |
| 동기화 작업 | 요청자, 대상, 대기·실행·완료·실패 상태, 결과 시각 |

파일은 사용자별 경로에 보관하고 DB에서 해당 사용자의 소유권을 확인해 제공한다.
R2 전체 저장소 키를 앱에 배포하지 않는다.
앱이 업로드를 요청하면 CF API가 특정 객체에 대한 짧은 유효기간의 업로드 권한을 발급한다.
다운로드도 인증된 API 또는 짧은 유효기간의 다운로드 URL로 제공한다.

학교의 서명된 파일 URL은 수집 시 사용하는 임시 위치다.
파일을 R2에 옮긴 뒤에는 R2 객체 키를 기준으로 조회 시 다운로드 경로를 발급한다.

첫 버전은 공지·과제·자료 목록과 문서 파일을 대상으로 한다.
동영상은 메타데이터를 동기화하고 파일 업로드는 별도 선택 기능으로 둔다.

## ChatGPT에서의 동작

일반 조회는 클라우드의 동기화본에서 처리한다.
답변·도구 결과에는 마지막 성공 동기화 시각을 함께 제공한다.

예시:

- 최근 공지 모아보기
- 이번 주에 추가된 강의자료 검색
- 여러 과목의 과제 마감일 정렬
- 동기화된 문서 검색과 다운로드
- 특정 강의 또는 전체 데이터 갱신 요청

사용자가 지금 새로고침을 요청하면:

1. MCP가 서버에 동기화 작업을 등록한다.
2. 앱이 주기적 작업 확인 또는 유지 중인 연결로 작업을 받는다.
3. 앱이 학교에서 최신 정보를 수집하고 업로드한다.
4. 서버가 작업 완료와 동기화 시각을 기록한다.
5. 다음 조회부터 갱신된 데이터를 사용한다.

앱이 오프라인이면 작업은 대기 상태로 남고, 다음 앱 실행에서 처리한다.
기존 동기화본의 조회와 파일 제공은 계속 가능하다.
외부 접속 경로가 필요한 노트북 직접 호출은 이 흐름에서 제외한다.

## 비용 구조

학교 로그인·수집·문서 다운로드 연산은 사용자 컴퓨터가 담당한다.
운영자에게 남는 비용은 CF API/MCP 요청, DB 저장·조회, R2 저장·요청이다.

비용을 조절하는 항목은 동기화할 강의 수, 요청 주기, 문서 업로드 범위,
파일 크기·보관 기간·버전 수다.
사용자별 저장량과 업로드량을 기록하고 서비스 제공 한도를 설정한다.
처음에는 메타데이터 동기화와 필요한 문서 업로드에 집중한다.

## 구현 순서

1. **수집 엔진 분리:** 기존 코드에서 학교 인증·조회·다운로드를 MCP 전송 계층과 분리한다.
2. **HTTP 전환:** 검증된 로그인 흐름을 적용하고 modulebuilder·ExternalTool·OCS 경로를 순서대로 옮긴다.
3. **로컬 동기화 실행기:** 주기 실행, 시작·복귀 시 갱신, 변경 감지, 중복 실행 방지, 실패 재시도를 구현한다.
4. **CF 동기화 API:** 사용자·기기 연결, 변경분 수신, DB 저장, R2 파일 업로드를 구현한다.
5. **원격 MCP:** 사용자 OAuth와 동기화본 기반 검색·조회·파일 제공을 구현한다.
6. **즉시 갱신:** 서버 작업 큐와 앱의 작업 수신·완료 보고를 연결한다.
7. **배포 가능한 앱:** 설치, 자동 시작, 동기화 주기·강의 선택, 저장량 표시, 기기 연결 해제를 제공한다.

## 후속 결정 항목

- 첫 배포 운영체제와 앱 형태: 트레이 앱, 백그라운드 서비스, 또는 둘의 조합
- 우리 서비스의 계정 로그인·OAuth 제공 방식
- 문서 자동 업로드의 기본 범위와 사용자별 제공 용량
- 파일 버전 보관 기간과 계정 삭제 시 DB·R2 정리 정책
- 서버 작업 수신 방식: 주기적 확인으로 시작할지, 연결 유지 방식으로 시작할지
